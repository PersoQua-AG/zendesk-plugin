**Architecture (mirrors the hardened M2–M4 pattern exactly — read `src/tools/cbp-list.ts`, `src/tools/screening.ts`, `src/tools/write-helpers.ts`, `src/tools/business-rules/rules.ts`, `src/register/business-rules.ts` first):**

- Each tool is a plain async function taking the Foundation seams as parameters: `(client: ZendeskHttpClient, cache: ResponseCache, params, securityLevel?)`. No module-level singletons.
- Zod validates every response envelope (`safeParse` → throw on malformed).
- **CBP list tools** (`list_articles`, `list_sections`, `list_categories`) are a single `listCbp(...)` call with a `makeDescribe(prefix, lineFn)` record screener — the canonical list-and-screen path. The glue (cursor loop, cap, screen, cache, summary) is **not** re-pasted; each tool is a ~14-line config object. Caps come from `DEFAULT_LIST_CAP`/`MAX_PAGE_SIZE`. Help Center list endpoints support cursor pagination when `page[size]`/`page[after]` are sent, which `listCbp` always does (see Self-review §ambiguity 1).
- **Single-record read** (`get_article`) runs `screenRecordDeep` inline exactly like `getUser`/`getView`, caches the screened copy, returns a `ReadResult`.
- **`search_articles`** is **not** CBP: `GET /help_center/articles/search` returns an offset-style `{ results, page, next_page, count }` envelope. It fetches one capped page and screens the results with `summariseScreened` — so it uses `makeDescribe` but not `listCbp` (see Self-review §ambiguity 2), mirroring M4's `list_slas` full-set-then-`slice` shape.
- **Creates** (`create_article`, `create_article_translation`, `create_section`, `create_category`) reuse M4's parameterized generic `createRule` (Task 1 exports it) — the four tools are thin wrappers that compute the (dynamic) collection path + `requiredFields`, render the body Markdown→HTML, and delegate. `createRule` already wraps the POST in `withAdminGuard`, so every Guide create is admin-gated by construction, screens the response before caching, and enforces `requiredFields` (parameterized in M4 specifically so articles can reuse it — PRD note). See Self-review §reuse-decision.
- **Updates** (`update_article`, `update_article_translation`) reuse `updateEntity` from `write-helpers.ts` — the plain-PUT tail (strip → empty-guard → PUT → parse-for-id → screen → cache → summary) with `guard: withAdminGuard`. Guide articles have **no `safe_update`** in the PRD, so these are plain PUT updates (not `safeUpdateWithConflict`). `update_article` keys on the numeric article id; `update_article_translation` keys on the **locale string** (`PUT .../articles/{id}/translations/{locale}`), which Task 1 enables by widening `updateEntity`'s `id` to `number | string`.
- **Markdown→HTML** for article/translation bodies uses the existing `markdownToHtml` (`src/util/markdown.ts`). A per-call `markdown` argument defaults to the global `markdownDefault` (`ctx.markdownDefault`, from `ZENDESK_MARKDOWN_CONVERSION`), resolved in the registrar exactly as `zendesk_add_comment`/`zendesk_create_ticket` do. `markdown:false` passes the caller's raw HTML through unchanged. `markdownToHtml`'s feature set is limited (see Dependencies — flagged).
- All Foundation/M1–M4 infra (`ZendeskHttpClient.request`, `cbpPageSchema`/`collectCbp`/`CbpPage`, `ResponseCache`, `listCbp`/`makeDescribe`/`screenRecordDeep`/`summariseScreened`/`makeScreener`/`SCREEN_WARNING`, `createRule`/`withAdminGuard`, `updateEntity`, `markdownToHtml`, `stripUndefined`, `ReadResult`/`okWithHandle`/`toText`, error classes, `DEFAULT_LIST_CAP`/`MAX_PAGE_SIZE`) is **imported, never reimplemented**.
- Tools register per-domain via a new `src/register/guide.ts` exposing `registerGuideTools(server, ctx)`, wired into `src/server.ts` after `registerBusinessRulesTools`, using the existing `ToolContext = { httpClient, cache, securityLevel, markdownDefault }`.

## Dependencies (flagged)

**No new runtime dependencies.** Two surgical reuse-enabling edits to reviewed M4 code (Task 1), both behavior-preserving and covered by the existing 254-test suite re-run:
1. Export `createRule` + `withAdminGuard` from `src/tools/business-rules/rules.ts` (currently module-private) so Guide creates reuse the generic instead of cloning the POST/parse/screen/cache glue. One `export` keyword per symbol; zero logic change.
2. Widen `updateEntity`'s `id` parameter in `src/tools/write-helpers.ts` from `number` to `number | string` so the locale-keyed translation-update path (`PUT .../translations/{locale}`) can reuse the shared update tail. Backward-compatible: every existing caller passes a number and is unaffected.

**FLAG — `markdownToHtml` feature ceiling.** The hand-rolled converter (`src/util/markdown.ts`) supports only: headings (`#`..`######`), unordered lists (`-`/`*`), inline `**bold**` / `*italic*` / `` `code` ``, and `[text](http(s)://…)` links, plus paragraphs. It does **NOT** support: tables, images, ordered lists, nested lists, blockquotes, multi-line code fences, or horizontal rules — all common in Help Center KB articles. **Per instruction, no Markdown dependency is added.** Guide handles rich content the pragmatic way: callers author rich articles as raw HTML and pass `markdown:false` (documented in the tool description); simple bodies use the default Markdown path. If reviewers want richer Markdown, extending `markdownToHtml` in-house (still dependency-free) is a separate task — flagged here, not folded in. This is a real limitation the orchestrator should acknowledge.

No Foundation touches: `ZendeskHttpClient.request` serves every Guide endpoint (all JSON GET/POST/PUT — no binary body, so `requestUpload` is not needed); `listCbp`/`cbpPageSchema`/`collectCbp` serve every CBP list; `screenRecordDeep`/`summariseScreened`/`makeDescribe` serve ingest screening; `ZendeskPermissionError` already exists in `src/client/errors.ts`; `security_level`/`markdown_conversion` are already env-wired in M1/M2.

```typescript
// src/tools/guide/articles.ts
// M5 Guide — articles + article translations. Read + create/update only (NO delete, per PRD §N1).
// Article/translation `body` is HTML in Zendesk; write tools convert Markdown→HTML (markdown flag,
// default from markdown_conversion) unless markdown:false (raw HTML passthrough). Creates reuse the
// M4 generic createRule (admin-gated by construction); updates reuse updateEntity. Every inbound
// record is screened at ingest by construction (title/body fenced; the rest passes through the
// field-agnostic deep screen).
import { z } from 'zod';
import type { ZendeskHttpClient } from '../../client/http-client.js';
import type { ResponseCache } from '../../client/cache.js';
import type { SecurityLevel } from '../../security/screen.js';
import { makeScreener, screenRecordDeep, summariseScreened, makeDescribe, SCREEN_WARNING } from '../screening.js';
import { listCbp, DEFAULT_LIST_CAP, MAX_PAGE_SIZE } from '../cbp-list.js';
import { markdownToHtml } from '../../util/markdown.js';
import { stripUndefined } from '../../util/object.js';
import { createRule, withAdminGuard } from '../business-rules/rules.js';
import { updateEntity } from '../write-helpers.js';
import type { ReadResult } from '../result.js';

// EN + DE are the confirmed first-class Guide locales (PRD §12 item 6). DEFAULT_LOCALE is applied
// when a create/translation omits a locale; any OTHER shape-valid locale string is still accepted
// (the register schema validates shape, not membership — Zendesk 422s a genuinely unknown locale).
export const DEFAULT_LOCALE = 'en-us';
export const GUIDE_LOCALES = ['en-us', 'de'] as const;

const ArticleSchema = z.object({
  id: z.number(),
  title: z.string().nullish(),
  body: z.string().nullish(),
  locale: z.string().nullish(),
  section_id: z.number().nullish(),
  author_id: z.number().nullish(),
  draft: z.boolean().nullish(),
  html_url: z.string().nullish(),
  updated_at: z.string().nullish(),
});
export type Article = z.infer<typeof ArticleSchema>;

// An article's untrusted free text is its title + body (HTML, author-controlled and rendered on
// read). Both keys are in ALWAYS_FENCE, so the deep screen wraps them unconditionally; the line
// renders from the SAFE copy so no raw payload leaks into the summary.
const describeArticle = makeDescribe<Article>('article', (a) => `#${a.id} ${a.title ?? '(untitled)'}${a.draft ? ' (draft)' : ''} [${a.locale ?? '?'}]`);

// Article/translation body is HTML in Zendesk. Convert Markdown→HTML when markdown is on (per-call
// flag defaulting to the global markdown_conversion). markdown:false → raw HTML passthrough.
function renderBody(body: string, useMarkdown: boolean): string {
  return useMarkdown ? markdownToHtml(body) : body;
}

export async function listArticles(
  client: ZendeskHttpClient,
  cache: ResponseCache,
  params: { pageSize?: number; maxRecords?: number } = {},
  securityLevel: SecurityLevel = 'standard',
): Promise<ReadResult> {
  return listCbp<Article>({
    client,
    cache,
    securityLevel,
    path: '/help_center/articles.json',
    key: 'articles',
    schema: ArticleSchema,
    describe: describeArticle,
    handle: 'zendesk_list_articles',
    cap: Math.min(params.maxRecords ?? DEFAULT_LIST_CAP, DEFAULT_LIST_CAP),
    pageSize: params.pageSize,
    label: (n) => `${n} article(s)`,
    errorLabel: '/help_center/articles',
  });
}
```

```typescript
const SingleArticleSchema = z.object({ article: ArticleSchema });

export async function getArticle(
  client: ZendeskHttpClient,
  cache: ResponseCache,
  params: { articleId: number },
  securityLevel: SecurityLevel = 'standard',
): Promise<ReadResult> {
  const raw = await client.request<unknown>(`/help_center/articles/${params.articleId}.json`);
  const parsed = SingleArticleSchema.safeParse(raw);
  if (!parsed.success) throw new Error('Unexpected /help_center/articles/{id} response shape.');
  const { value, flagged } = screenRecordDeep(parsed.data, (key) => `article-${params.articleId}-${key}`, makeScreener(securityLevel));
  const safe = value as { article: Article };
  const entry = cache.save('zendesk_get_article', safe);
  return {
    summary: `Article #${safe.article.id} ${safe.article.title ?? '(untitled)'} [${safe.article.locale ?? '?'}]${flagged ? SCREEN_WARNING : ''}`,
    cacheHandle: entry.handle,
    flagged,
  };
}
```

```typescript
const ArticleSearchSchema = z.object({ results: z.array(ArticleSchema) });

export async function searchArticles(
  client: ZendeskHttpClient,
  cache: ResponseCache,
  params: { query: string; locale?: string; perPage?: number },
  securityLevel: SecurityLevel = 'standard',
): Promise<ReadResult> {
  if (params.query.trim() === '') throw new Error('search_articles requires a non-empty query.');
  // Search is offset-style (not CBP). Fetch one defensively-capped page; per_page is clamped to the
  // Zendesk per-page maximum so an oversized result set cannot push an unbounded array into cache.
  const perPage = Math.min(params.perPage ?? MAX_PAGE_SIZE, MAX_PAGE_SIZE);
  const parts = [`query=${encodeURIComponent(params.query)}`, `per_page=${perPage}`];
  if (params.locale) parts.push(`locale=${encodeURIComponent(params.locale)}`);
  const raw = await client.request<unknown>(`/help_center/articles/search.json?${parts.join('&')}`);
  const parsed = ArticleSearchSchema.safeParse(raw);
  if (!parsed.success) throw new Error('Unexpected /help_center/articles/search response shape.');
  const capped = parsed.data.results.slice(0, perPage);
  const screened = summariseScreened(capped, describeArticle, securityLevel);
  const entry = cache.save('zendesk_search_articles', { results: screened.records });
  // The query echoed in the summary is caller-authored (trusted), not attacker-controlled Zendesk
  // content, so it is safe unscreened; the result lines render from the SCREENED records.
  return {
    summary: `${screened.records.length} article(s) matching "${params.query}":\n${screened.lines.join('\n')}${screened.warning}`,
    cacheHandle: entry.handle,
    flagged: screened.flagged,
  };
}
```

## Self-review

**Reuse decision — `createRule` vs a parallel `createArticle`:** **Reuse `createRule`.** M4 explicitly parameterized `createRule` with `requiredFields: string[]` (not a hardcoded `title`) so articles/sections/categories/translations reuse it — article create requires `title+locale+body`, translation `locale+title+body`, sections/categories `name+locale`, all expressible via `requiredFields`. `createRule` also bakes in `withAdminGuard`, which is exactly right for Guide (article/section/category/translation management requires Guide manager / admin). The only enabler needed was exporting `createRule` + `withAdminGuard` (they were module-private in `rules.ts`) — Task 1, a one-`export`-keyword change with zero logic change. The dynamic collection path (section-/article-/category-scoped) slots straight into `createRule`'s `${collection}.json` builder. A parallel `createArticle` would clone ~20 lines of POST/parse/screen/cache glue for no benefit and drift from the hardened path. **Alternative considered:** promoting `createRule` into `write-helpers.ts` as a `createEntity` twin of `updateEntity` (more cohesive long-term home, avoids a guide→business-rules import) — rejected as more M4 churn than the instruction ("reuse the parameterized createRule generic") warrants; flagged here should reviewers prefer it. Updates reuse `updateEntity` (already exported, generic, guard-capable) per instruction; the only enabler was widening its `id` to `number | string` for the locale-keyed translation path.

**Locales (EN + DE default):** `DEFAULT_LOCALE = 'en-us'` is applied by the create/translation tools when a locale is omitted; `GUIDE_LOCALES = ['en-us','de']` documents the first-class set (PRD §12 item 6). The register-boundary `localeSchema` validates locale **shape** (`/^[a-z]{2,3}(-[a-z0-9]{2,4})?$/i`, matching `en-us`, `de`, `fr`, `pt-br`, …) but **not membership**, so any valid locale is accepted; a genuinely unknown locale surfaces as Zendesk's 422 (`ZendeskValidationError`). Not hardcoded to two.

**Markdown bodies:** article/translation `body` is HTML in Zendesk; `renderBody(body, markdown)` calls `markdownToHtml` when markdown is on, else passes raw HTML through. The per-call `markdown` flag defaults to `markdownDefault` (from `markdown_conversion`), resolved in the registrar exactly as `zendesk_add_comment`/`zendesk_create_ticket`. Section/category `description` is plain text — no rendering path.

**`markdownToHtml` sufficiency — FLAGGED (see Dependencies):** the hand-rolled converter supports headings, unordered lists, bold/italic/inline-code, and http(s) links only. It does **NOT** support tables, images, ordered lists, nested lists, blockquotes, code fences, or horizontal rules — all common in KB articles. No Markdown dependency is added (per instruction). Rich articles are authored as raw HTML via `markdown:false` (documented in the `create_article`/`update_article` tool descriptions). Extending `markdownToHtml` in-house is a possible follow-up, flagged for the orchestrator — not folded in.

**M5-scope ambiguities (each with a proposed default):**
1. **Help Center list pagination style.** Help Center list endpoints (`/help_center/articles`, `/sections`, `/categories`) support cursor pagination when `page[size]`/`page[after]` are sent (which `listCbp` always does), returning the `meta.after_cursor`/`links.next` envelope. **Default: `listCbp` (CBP).** Risk: if a given account/endpoint returns an offset-only `{…, page, next_page}` envelope instead, `cbpPageSchema.safeParse` fails with a clear "Unexpected /help_center/… response shape." error. **Flag for verification against live/fixtures**; if CBP is not honored, fall back to the offset single-page shape used by `search_articles`.
2. **`search_articles` is not CBP.** `/help_center/articles/search` is offset-style (`{results, page, next_page, count}`). **Default: fetch one `per_page`-capped page (≤100), screen, cache** — mirrors M4 `list_slas`. If a caller needs beyond one page, add offset paging (`page=`) — flag as a follow-up, not folded in.
3. **Article create requires `body`.** `requiredFields: ['title','locale','body']` — a body is required at create. **Default: require body.** If the team wants to allow empty-body drafts, drop `'body'` from `requiredFields` — flag as a product decision.
4. **Translation update endpoint (locale-path vs numeric translation-id).** Zendesk offers both `PUT .../articles/{id}/translations/{locale}` (article-id + locale) and `PUT /help_center/translations/{translation_id}` (numeric). The PRD §6 row lists `.../articles/{id}/translations`, so **default: the locale-path variant** (ergonomic — caller knows article id + locale; no extra lookup). This is what drove the `updateEntity` `id` widening. If a numeric-id path is preferred later, it needs a list-translations read tool (not in the M5 inventory) to obtain the id — flag.
5. **Guide-manager vs admin wording in the 403 re-map.** Reusing `withAdminGuard` yields the generic "requires an admin role" message. Guide management actually requires the **Guide manager** role (admin-equivalent). **Default: reuse the generic message** (accurate enough — Guide managers are elevated/admin-class users; the tool descriptions say "Guide manager/admin"). If a Guide-specific message is wanted, pass a custom guard — flag as cosmetic.
6. **`update_article` scope (no section move / locale change).** `update_article` supports `title`/`body`/`draft` only; moving an article between sections or changing its source locale is out of scope. **Default: metadata/body update only.** Add a `section_id` move field later if needed — flag.
